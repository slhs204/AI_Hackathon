# Phishing Coach 後端進度報告

## 1. 一句話總結

後端已經可以用：它包住 Albert 的規則引擎，再加上 AI、證據驗證、公司流程和評估。在 200 封**沒人看過的公開釣魚資料**上，規則只抓到 18%；加上 AI 後，釣魚信幾乎全抓到。目前最好的組合是 **Haiku + prompt v2 + 「只有緊急用語算備註」**：在調整組上釣魚信抓到 **96%**、誤報 **0%**。最終數字還要在測試組上跑一次才算數。

## 2. 做了什麼

### 2.1 後端（`backend/`，FastAPI，可部署到 Cloud Run）

| 端點 | 做什麼 | AI 模型 |
|---|---|---|
| `GET /health` | 確認服務正常 | — |
| `POST /triage` | 依寄件人、主旨、預覽替收件夾排優先度（最多 50 封） | Claude Haiku 5.5 |
| `POST /analyze` | 單封信的完整分析：紅旗、原文證據、公司流程、練習題 | Claude Sonnet 5.5（可換成 Haiku） |
| `POST /challenge` | 使用者補充背景後，重新評估某一個紅旗 | Claude Sonnet 5.5 |

**分析流程（`/analyze`）：**
1. Albert 的 8 個規則偵測器（v3.1，原封不動）
2. 補上規則沒有的檢查：`javascript:` 連結、`真網址@假網址` 的偽裝、「change my salary account」、網域裡藏公司名
3. AI 最多補 3 個紅旗，再加上摘要和白話說明
4. **每段引文都對照信件原文驗證**，對不上就丟掉，並標「分析不完整」
5. 套用公司流程當「下一步」，附一題同類型的練習題
6. **只有緊急用語、沒有要求任何動作時，列為備註，不算紅旗**（新）

### 2.2 相容三個前端

後端同時支援 Albert 的 v3.1 擴充功能和 Outlook 面板、Albert 的舊原型，以及 Jenessa 的 Hookline。兩種 JSON 格式都收，回傳的欄位也涵蓋兩邊畫面要讀的東西。

### 2.3 安全與隱私設計

- **Token 沒設定就拒絕**（跟 Albert v3.1 一致），而且在呼叫任何付費模型之前就檢查
- **AI 不能刪除規則抓到的紅旗**，也不能把信判成「安全」
- 信件內容一律標示為「不可信的資料」，AI 不會執行信裡藏的指令
- 不記錄信件內文，只記錄 ID、數量和時間
- 限制請求大小、模型輸出長度、逾時時間和呼叫次數
- `/triage` 只看寄件人、主旨、預覽，而且只在使用者要求時才跑

### 2.4 測試

71 個自動化測試，全部通過。涵蓋：證據驗證、整個分析流程、token 和 CORS、兩種前端格式、Claude 呼叫（用假的 SDK）、錯誤處理、誤報控管。

## 3. 評估

### 3.1 測試資料

| 資料集 | 數量 | 來源 | 用途 |
|---|---|---|---|
| 核心測試集 | 23 封 | Albert 的 10 封範例＋我手寫的 13 封（含誤報測試、被盜用的廠商帳號、信件串劫持） | 薪資詐騙情境 |
| 盲測集 | 200 封（100 釣魚＋100 正常） | 公開資料集 [Teddyha](https://huggingface.co/datasets/Teddyha/phishing_benign_email_dataset)（MIT 授權），團隊沒人寫過或依它調整規則 | 誠實的類化測試 |

為了避免「在同一批信上調整又測試」造成分數灌水，盲測集分成兩半：**調整組**（50+50）和**測試組**（50+50，最後只跑一次）。

### 3.2 結果（Gmail 視角：只有擴充功能讀得到的內容）

**盲測集，調整組（100 封）**

| 設定 | 釣魚信抓到 | 正常信誤報 | 怎麼量的 |
|---|---|---|---|
| 只用規則（舊） | 10/50 | 3/50 | 實際執行 |
| Sonnet + prompt v1 | 50/50 | 12/50（24%） | 實際執行 |
| Haiku + prompt v1 | 49/50 | 4/50（8%） | 實際執行 |
| Haiku + prompt v2 | 49/50 | 3/50（6%） | 實際執行 |
| **Haiku + prompt v2 + 緊急用語規則** | **48/50（96%）** | **0/50（0%）** | 用存好的結果離線重算* |
| Sonnet + prompt v1 + 緊急用語規則 | 48/50 | 10/50（20%） | 用存好的結果離線重算* |

\* 緊急用語規則只是在 AI 回應之後做固定的後處理，所以可以用存好的每封信結果直接重算，不用再呼叫 API。

**盲測集，全部 200 封**

| 設定 | 釣魚信抓到 | 正常信誤報 |
|---|---|---|
| 只用規則，有附件資訊 → 加緊急用語規則後 | 34/100 → 27/100 | 5/100 → 0/100 |
| 只用規則，Gmail 視角 → 加緊急用語規則後 | 18/100 → 8/100 | 5/100 → 0/100 |
| Sonnet + v1（Gmail 視角） | 100/100 | 24/100 |

**核心測試集（23 封）**

| 設定 | 釣魚信抓到 | 正常信誤報 |
|---|---|---|
| 只用規則（加緊急用語規則後） | 13/14 | 1/7 |
| Sonnet + v1 → 加緊急用語規則後 | 14/14 | 3/7 → 2/7 |

### 3.3 學到什麼

1. **規則只擅長它被寫來對付的東西。** 遇到熟悉的 Acme 薪資詐騙很準，但遇到沒看過的一般釣魚信（假 Google、Dropbox、銀行），只抓到 18%。
2. **AI 補上了漏抓。** 規則完全抓不到的「被盜用的真廠商帳號」，Sonnet 找出了兩個紅旗，引文也都驗證通過。
3. **Sonnet 比較容易誤報，Haiku 比較保守。** 同樣用 prompt v1，Sonnet 誤報 24%，Haiku 只有 8%。
4. **v2 讓 Haiku 更精準**：誤報再降，引文驗證失敗也從 3 次降到 0。
5. **剩下的誤報其實來自規則，不是 AI。** 「緊急用語」偵測會把真的 CFO 截止通知也標起來。改成「只有緊急用語算備註」之後，誤報歸零。
6. **取捨要說清楚：** 緊急用語規則讓「只用規則」模式少抓了 10 封釣魚信（18 → 8）。所以這條規則要搭配 AI 一起用，不能單獨靠規則。
7. **AI 引文驗證有用：** Sonnet 的 264 個紅旗和 Haiku v2 的 50 個紅旗，引文全部對得上原文；Haiku v1 有 3 個對不上，被驗證機制抓到並丟掉了。
8. **速度：** 每封信 Haiku 約 1.7 秒，Sonnet 約 2.8–3.7 秒（中位數）。
9. **擴充功能如果送出附件檔名**，只用規則就能多抓 16 封（惡意附件從 1/13 變成 10/13）。

## 4. 自我檢查修好的錯誤

| 錯誤 | 影響 |
|---|---|
| 沒有 Claude key 時，`/analyze` 會回 HTTP 500 | demo 時 key 沒設好，整個分析就會掛掉 |
| 盲測轉換時漏讀附件，數字被低估 | 報告不公平（18% → 有附件資訊時其實是 34%） |
| 會重試不該重試的錯誤 | 白花錢 |
| API 文件的範例數字是編的 | 組員照著寫會對不上 |
| 200 KB 大小限制可以被繞過 | 安全漏洞 |
| 文件數值過時 | 誤導 |

## 6. 誠實的限制

- 所有測試信都是合成或公開資料，**不代表真實世界的準確率**，也還沒量過「使用者有沒有學會」
- 測試組還沒跑過，**96% / 0% 只是調整組的數字**
- Sonnet + prompt v2 還沒測過
- **Tinker 還沒真的呼叫過**
- 兩個擴充功能都還沒在瀏覽器裡實際接上後端
- 還沒部署到 Cloud Run（我沒有 GCP 權限）

## 7. 需要團隊決定

1. **部署哪個後端**：`backend/`，還是 Albert v3.1 的 `main.py`
2. **單封信分析用哪個模型**：Haiku + v2（更準、更快、便宜約 20 倍），還是 Sonnet
3. **要不要把 prompt v2 設成預設**（目前預設還是 v1）
4. **什麼時候跑測試組**（最後一次，報告和 pitch 用的數字）：Haiku 約 $0.1，Sonnet 約 $1.5
5. **Tinker 要不要也接上測試**（贊助商額度）
6. **要不要接 Tranco 網域排名**（要先確認授權）
7. **擴充功能要不要送附件檔名**
8. **Albert 規則的漏洞**：要改他的 engine，還是繼續由後端補
